# Usage reservations and error logging preparation

Local preparation dated 4 October 2026. Participant AI remains disabled by default, the existing release/admission/consent checks remain intact, and no provider call, cloud resource or paid test was made. Nothing here establishes deployed enforcement, anonymity, complete telemetry control or clinical readiness.

## What changed

`src/lib/ai/journey-usage-reservation.ts` contains a dormant provider-neutral accounting decision and a transactional storage interface. It is not imported by the participant endpoint or used by the app. There is no production storage adapter. It is ready for fictional tests and later integration after admission identity, a permitted provider, its verified maximum charge and a small approved budget are settled.

Application-owned server and browser error paths now emit fixed diagnostic codes. `safe-error-reporting.ts` drops arbitrary exception messages, causes, stacks, routes, URLs and caller context. `server.ts` explicitly initializes sanitisation before importing the server framework, so the package's `sideEffects: false` setting cannot discard a side-effect-only import. The former process-wide raw “last error” cache was removed. The root error component uses the same bounded code helper. The existing journey generation/boundary/transport already discard exception text and return whitelisted failure codes; those policies and contracts remain unchanged.

On the server, `console.error` preserves only an exact two-argument `BFA_EVENT` plus allowlisted-code message. Other `console.error` arguments and all `console.warn` arguments are **dropped**, including third-party framework diagnostics, and replaced by a generic category. This sacrifices raw debugging detail intentionally; it is not intelligent redaction. Browser forwarding passes only a fixed code to existing optional hooks and catches reporter failures. No settings were changed in hosting or provider accounts.

## Accounting contract and invariants

| Concern                    | Prepared behaviour / requirement                                                                                                                                                                                                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per-person and shared caps | Request counts and reserved spending checked for participant/day, participant/pilot, global/day and global/pilot. All scopes must approve together.                                                                                                                                                                        |
| Amounts                    | Integer millionths of one configured currency (CAD or USD). Totals use integer arithmetic. No current price, exchange rate or default paid budget is supplied.                                                                                                                                                             |
| Reservation basis          | A reviewed **maximum possible charge** for one bounded call, including billable input, output/reasoning and any other billable component. This is reserved capacity, **not actual spending or an invoice**. Character ceilings and average token estimates are not proven maximum prices.                                  |
| Concurrency                | One durable serializable transaction covers shared budget counters, participant counters and attempt uniqueness. A provider can be created/called only after the transaction has committed and returned a new reservation. Independent processes must see the same authoritative state.                                    |
| Idempotency                | A server-issued attempt ID is bound to a participant, keyed request fingerprint and pricing version/amount. Duplicate IDs never grant another dispatch; conflicting bindings are rejected. A retry after midnight still cannot dispatch twice.                                                                             |
| Ambiguous failures         | A timeout, rejected output, thrown provider error or lost commit acknowledgement never automatically refunds, expires or reissues a reservation. A consumed reservation can remain unused when the process fails before dispatch; that conservative loss prevents a duplicate charge.                                      |
| Daily rollover             | Uses the server's UTC calendar date, independent of the participant's device. Daily scopes change; pilot totals and attempt uniqueness remain. UTC is a proposed accounting convention and does not alter user-facing Toronto dates.                                                                                       |
| Missing/corrupt state      | Fails closed. Request handling cannot silently initialise a missing budget or turn a storage failure into permission.                                                                                                                                                                                                      |
| Stored data                | Opaque random IDs or secret-key HMACs, accounting date, pricing version and reserved amount only. No teaching, selected labels, answer payloads, private writing, response text, exception text, email or IP. Pseudonyms and keyed fingerprints still need access/retention controls; they are not a promise of anonymity. |
| Refunds/reconciliation     | Not implemented. Reservations remain fully charged to allowance throughout this budget, even when actual billing is lower. Any future controlled reconciliation must preserve at-most-once dispatch and all cumulative caps; do not infer no charge from an HTTP error or client disconnect.                               |

The store interface is an engineering obligation, not evidence of durable storage. The test fixture is explicitly an in-memory **test-only simulation** of serialization and never an acceptable deployed allowance. An adapter may use an appropriate transactional database later, but it must guarantee atomic commit across all scopes and unique attempts, durable retention through restart, and consistent reads across concurrent instances. Storage callback retries must remain pure: never generate a response from within a database transaction callback.

The current pilot admission uses a signed unlocked session and does not yet provide a durable verified per-participant identity. Do not use an anonymous browser ID or the shared gate password as proof of a person, and do not add an untrusted participant field to the four-field AI input contract. Resolve identity/admission deliberately before connecting this limiter. Server-issued attempt IDs need a reviewed retry lifecycle; minting a new ID on every HTTP retry defeats attempt deduplication even though total caps would still bound reservations.

## Offline verification

```sh
npm test -- --no-cache src/lib/ai/__tests__/journey-usage-reservation.test.ts src/lib/__tests__/safe-error-reporting.test.ts
```

The two suites passed **18 tests** locally. They cover all four count/spend scopes, the exact monetary boundary, independent participants/daily rollover with permanent pilot totals, concurrent global and duplicate attempts under a serialized mock transaction, ambiguous dispatch failure, lost commit acknowledgement, invalid ledgers, missing/malformed stores and bounded errors. Logging tests inject fictional private-writing/credential sentinels and hostile error getters into console and browser reporters; output remains only fixed codes. No actual database, participant payload, model request or billing transaction is exercised.
