# P5 server/session contract proposal — 27 October 2026

This is a proposed implementation and acceptance contract for a future bounded developer voice route. It is not implemented server authority, live-test approval, a provider selection, a budget, or participant-release acceptance. Current controls, lifecycle ports and browser tests remain offline preparation. No route, provider session, recording, authentication setting or database change is enabled by this document. The live approval gate remains unset: `scripts/conversation-eval/approval-grants.json` is empty and the draft manifest's approval and expiry are null. P4's text-evaluation approval, if later granted, would not authorize voice.

## Authority before a live route

- Define the concrete developer-only route, admitted identities, provider/session implementation, limits, expiry, accounting and evidence plan before requesting its separate bounded approval. Do not reuse the closed v5 allowance or infer paid authorization from general development instructions.
- Derive identity from verified server authentication; check the server-controlled expiring allowlist, ownership and current thread incarnation/revision. Client store IDs, `VoiceAttempt`, `getThreadLifecycleBinding()` and a visible button are coordination data, not admission authority. Reject forged, expired, revoked, replayed, cross-owner and deleted-thread requests, including after a lock wait or other asynchronous boundary.
- Keep credentials and privileged admission/settlement on the server. Bind any narrowly scoped client capability to the authorized owner, thread, attempt/session, operation and expiry; its transport and replay protection require review for the chosen provider. Do not invent a browser-side secret or assume a provider supports a particular capability.
- Preserve the existing P3b ownership/RLS and transactional reserve/claim/settle/finish rules when reusing that boundary. Its active sealed authority currently expires after 15 minutes; voice must not silently extend it. A new voice lease lifetime or schema requires an explicit design. In-memory controller state and P4's single-host evaluator ledger do not establish production dispatch or accounting guarantees.
- Revalidate admission before connection and activation, after pending input enabling, and before each further authorized dispatch. Admission itself must open no paid connection. Future streaming/reconnect behavior needs an explicit revocation and expiry plan; the current ports do not supply one.

## One owner for work and resources

`ConversationService` remains the context, source/grant and cancellation authority. Provider inputs must pass through P1 context assembly; voice must not introduce hidden memory, alternate context assembly or new source authority. Use the exact shared voice model and coordinator, retaining the selected record separately from the attempt that owns resources.

Each acquired admission, capture, connection and playback handle has an explicit owner until closure is confirmed. Return late/partial handles for cleanup, or clean them before rejecting acquisition. Retain removed/replaced owned tracks and failed handles; do not create untracked track clones or background capture. A permission request or input-state change can remain pending after abort. Do not release ownership, rebind a new attempt or offer private-practice assurance while acquisition, input change, cancellation or closure remains uncertain.

Stop fences pending typed and spoken work and clears queued output. Mute changes input only. Pause requests shutdown; Finish talking and Type instead request shutdown while preserving the conversation's text identity. Type instead may expose the text controls without claiming that voice cleanup succeeded. Delete/Clear fence and purge content immediately while resource cleanup continues; later results must not recreate deleted content or cancel a new record that reused its ID. Only explicit Retry retries failed cancellation/closure, and it must acquire no new resource. Start/Resume require deliberate action and confirmed previous cleanup; reconnect, network recovery, page restoration and account changes must never start voice automatically.

## Provider termination, callbacks and accounting

- Distinguish local input suppression, local track termination, playback cancellation, transport closure and provider session termination. A fulfilled browser close or `AbortSignal` does not establish stopped provider work, zero remaining charge or zero retention. A future adapter must define what evidence each close promise represents; unknown termination remains visible and retryable.
- Keep possibly dispatched work charged/reserved as uncertain until server reconciliation establishes the outcome. Use durable, idempotent admission and usage evidence appropriate to the selected deployment. Preserve content-free settlement/tombstone evidence after deletion; do not release a hold merely because the UI left voice mode. Usage estimates and receipts must not be described as invoices or guaranteed zero cost.
- Authenticate provider callbacks using the chosen provider's verified contract. Bind events to server-owned session/attempt, owner, thread incarnation/revision and output generation. Reject forged, duplicate, replayed, stale and out-of-order effects; a late disconnect must not stop a resumed attempt. Cancellation/deletion wins over a late answer. Only committed current-origin answers may enter the playback queue or conversation context, and unheard output must remain distinguishable from output actually played.

## Content and evidence limits

The current capture adapter records and stores no audio. Preserve that default: no durable audio, hidden transcript archive, automatic save, content-bearing diagnostic logs or background recording. Temporary audio/transcript buffers need explicit ownership, bounded lifetime and purge on stop/delete/account change. Finalized transcript use follows deliberate existing transcript-choice semantics; only explicit Save persists the permitted sealed conversation state. Do not silently add private practice, partial/unconfirmed speech, journals, weekly notes or other hidden content to context. Provider retention settings and actual retention evidence require separate verification; local deletion is not a claim about provider retention.

## Acceptance before changing the gate

- [ ] Review the concrete route, provider contract, identity/expiry checks, bounded approval, termination semantics and durable accounting together. Confirm denial creates no capture/paid dispatch and expired/revoked authority cannot resume.
- [ ] Test actual server boundaries for forged/cross-owner/replayed authority, expiry across waits, duplicate dispatch, failed/lost responses, Stop/Delete during dispatch and reconciliation after deletion. Retain uncertainty when evidence is absent.
- [ ] Exercise late permission, connection and input completion; reused thread IDs; stale callbacks; account change; navigation/unmount; offline/recovery; selected-versus-owned attempt changes; failed cancellation/close; explicit retry without reacquisition; and no automatic Resume.
- [ ] On physical supported devices, inspect permission denial/dismissal, microphone indicators, mute versus stop, device removal, interrupted input, backgrounding and cleanup after leaving. Confirm only this attempt's resources are claimed closed; other tabs/devices are outside that assurance.
- [ ] With a listener, verify audible interruption, queued-output removal, no stale audio after switch/delete, and played-versus-unheard transcript attribution. Correlate provider termination/usage evidence separately.
- [ ] With actual keyboard and screen-reader users/tools, verify action names, focus retention/recovery, status/error announcements, touch layout and availability during startup/shutdown failure. Chromium layout/DOM checks and synthetic resources alone do not establish this acceptance.
