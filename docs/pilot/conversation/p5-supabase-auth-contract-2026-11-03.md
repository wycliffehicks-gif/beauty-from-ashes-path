# P5 Supabase Auth integration decision — 3 November 2026 UTC

Status: provider-specific research complete; production integration **not ready**. This is a design/evidence change only. Application source remains the tested `7973d90aad7b0546a2a821214524d4412fb22d71`. No live Auth request, credentials read, connected SQL/configuration change, provider call or activation was performed.

## Decision

Keep P5 inactive. The existing middleware is not the complete P5 Auth contract. An explicit request-bound `getClaims(token)` plus `getUser(token)` can supply useful verification, but cannot by themselves establish transaction-coherent current policy, durable P5 revocation or continuing provider eligibility. Do not implement a generic wrapper claiming those guarantees.

Separate the durable Auth-session revocation identity from the bounded voice-authority lifetime in the next offline design. Refresh preserves the Auth session ID in the inspected provider source; the existing insert-once P5 row permanently denies that same pair after its at-most-15-minute expiry. This would prevent a later voice visit during the same login. Do not renew, erase or reactivate that row, invent a replacement Auth ID, silently use an episode ID as `sessionId`, or force re-login as a workaround. First evaluate reuse of existing issuance/claim identities; a new episode table is not yet selected or justified.

The existing implementation remains valid evidence for its narrower one-fence contract. The new finding limits its suitability for the eventual returning-user experience; it does not erase completed P5 tests or authorize replacing retained fences/holds.

## Required future host contract

1. Derive identity from the actual request. Keep the exact bearer server-only and use it explicitly for both claims and fresh user verification on every mandatory Auth invocation. Never refresh it mid-operation or cache a success as continuing authority. Fail closed on unavailable/malformed/late evidence. Do not log tokens, user content or credentials.
2. Obtain a protected, exact `(owner, Auth session)` observation plus the effective policy needed to calculate a conservative eligibility ceiling. The ceiling is no later than JWT expiry and any established applicable bound; local P5 configuration may only shorten it. Unknown policy is not an unlimited lifetime. Account deletion/ban, current session ownership, timebox, inactivity, single-session and relevant AAL changes need explicit semantics. No refresh token belongs in this path.
3. Preserve the existing monotonic time, shrinking eligibility, initial/final Auth checks and local terminal fences. External Auth requests and SQL are separate observations: even an Auth/read/Auth sequence has a race afterward. To claim immediate revocation exclusion at a database operation, establish a transaction-coherent predicate/locking protocol against relevant Auth state or a proven synchronous terminal-fence bridge. An HTTP check followed by SQL, or asynchronous webhook alone, cannot prove it.
4. For deliberate app logout, synchronously cancel local work and retain exact server identity/reconciliation evidence before tokens disappear. The future host must persist the terminal P5 revocation and address provider stop separately. Lost responses mean uncertain completion; they never authorize release/refund or a replacement operation. Remote/global/admin/password/security changes need durable enumeration/delivery plus idempotent monotonic fencing. Arbitrary profile edits need an explicit policy, not automatic blanket revocation.
5. Revocation stops future authority; it does not prove an already-running provider session ended. Authenticated whole-operation provider finality, exact retained cleanup and cumulative accounting remain separate acceptance gates.

These are implementation requirements, not installed behavior. A service-only RPC taking arbitrary owner/session values is not self-authenticating. A proposed Auth-schema query/trigger also needs platform support, permission review and deadlock/lock-order analysis before it can be a solution. An unavailable/ambiguous Auth lookup denies the current operation but is not proof of permanent revocation. Temporary bans, password/email changes and ordinary metadata edits need distinct reviewed semantics; do not silently turn every denial into a permanent tombstone or promise that unbanning restores a terminal identity.
